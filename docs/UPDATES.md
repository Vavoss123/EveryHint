# Windows release updates

P11 includes a manual **Check for updates → Download → Restart and install** flow with progress, cancellation, failure reporting and native restart confirmation. It uses pinned **electron-updater 6.8.11** with the full NSIS installer. The user explicitly chose to **keep updates unconfigured until signing and hosting are ready**. `resources/windows-updates.json` therefore ships disabled with no URL, publishers or key. No update network request, background check, automatic download or quit-time installation occurs in this build. Settings shows the reason; trusted IPC also refuses actions while unconfigured.

## Trust and permission boundaries

- The public policy is compiled into the main application, never read from renderer input, user documents, environment URLs or a remote manifest. Activation requires packaged Windows, an HTTPS feed without URL credentials/query/hash, expected full Windows certificate subject(s), and a pinned Ed25519 manifest public key. Do not put secrets in this policy.
- Check is explicit and separate from download. Even “no new version” metadata must authenticate. Only a newer stable numeric version, one basename-only EveryHint full `.exe`, bounded size/SHA-512 and no web-installer package are accepted for download. No prerelease, downgrade, arbitrary host/file URL or elevation/web payload is accepted.
- electron-updater auto-download, quit-time auto-install, prereleases and downgrades are disabled; web installers are disabled. Its logger is disabled. Update responses do not become AI context or permissions.
- This stable updater version predates upstream v27 signed manifests. EveryHint explicitly verifies its own versioned canonical JSON payload with the pinned Ed25519 key before permitting download. It does **not** claim v27 behavior. Current upstream documentation describes next/v27; installed 6.8.11 source/types were inspected.
- Downloads use the updater's SHA-512 checks and strict Windows signature hook. EveryHint independently rehashes/rechecks exact size and valid full publisher subject after download, before restart confirmation, and again immediately before install. Signature inspection runs the system PowerShell directly, hidden, with fixed encoded source and the path only in the child environment; module lookup is restricted to Windows system modules. Timeout, command/JSON/verification failures all reject. No legacy “unsupported PowerShell, skip verification” fallback is accepted. The private unsigned installer is actually rejected by this verifier.
- Install requires a fresh native “Restart and install” confirmation, defaults to Later, stops capture/remote inference and flushes encrypted meeting writes before locking stores. The existing bounded app quit barrier awaits teardown. Encrypted data, model cache and account keys are outside installer replacement. Preservation is configured and covered by existing local storage tests; real signed upgrade/rollback on clean Windows is still pending.
- Check/download requests can be cancelled; stale progress/results cannot enable install. New actions wait for cancelled work to finish. Cached downloads cannot install on ordinary quit/restart. No endpoint, certificate, release key or publisher identity was fabricated, and no release was published.

## Release operator setup (pending prerequisites)

1. Establish a controlled HTTPS static release directory and secure Windows signing pipeline. Obtain an approved Authenticode identity and an independently managed Ed25519 release-metadata keypair. Record the **full Subject string** returned by Windows for the signing certificate, not just a display name. Review key rotation, provider distribution rights and licenses. None is supplied by this repository.
2. Set the public fields in `resources/windows-updates.json`: `enabled: true`, real `feedUrl`, `publisherNames` and PEM SPKI `manifestPublicKey`. Package only the public key. Private keys belong in protected operator/CI secret storage. Never configure a private token in the renderer/policy/feed URL. The current disabled JSON is intentional, not a placeholder production endpoint.
3. Use a reviewed secure production build/signing process. The existing `dist:win` command deliberately disables signing and labels outputs private/unsigned; it is **not** that production signing process. Keep the stable application ID/per-user NSIS upgrade behavior, sign the application, helper and installer, preserve the trusted policy/config inside ASAR, and verify the final signatures. Do not publish private artifacts as trusted releases.
4. Generate authenticated metadata from the **already signed** installer and matching release private key. The operator utility checks Windows publisher trust and key/public-policy agreement; it neither creates a key nor uploads anything. Choose a new output path (exclusive create):

   ```powershell
   node scripts/sign-update.mjs <signed-installer.exe> <version> <private-key.pem> <new-latest.yml>
   ```

   This writes JSON (valid YAML for the generic updater provider), containing `version`, exactly one `files` entry (`url`, `sha512`, `size`), and `everyhintSignature`. Canonical signed bytes are `releasePayload` in `src/main/updates-policy.ts`: schema 1, version, files, and optional `minimumSystemVersion` (null when absent), in that property order. Do not edit authenticated fields after signing. The utility rejects a disabled/incomplete policy, unsigned installer, wrong key or existing output. It does not overwrite or publish metadata. If adding a minimum OS gate, include it before signing through the same canonical function; the current utility emits no gate.
5. Stage metadata as `latest.yml` and its exact installer basename in the authorised HTTPS directory. Review/upload separately; no automatic publishing workflow exists. HTTPS plus a checksum alone does not authenticate mutable metadata. Match the pinned key and Windows publisher policy.
6. Perform real signed-host acceptance: newer/current/unsupported OS; unsigned/tampered/wrong-key metadata; checksum/size/publisher mismatch; offline/interrupted/cancelled transfer; cached-file mutation; native Later/Restart; active meeting flush; standard-user upgrade/uninstall/data preservation; failed install/recovery and rollback policy. Only then enable distribution. This work has fixture/crypto/local unsigned-rejection evidence, **no genuine signed-feed/download/install evidence**.

Key rotation requires a reviewed bridge release or reinstall path because existing installs pin their key/subjects. The current policy supports up to four Windows publisher subjects but one Ed25519 key; there is no automatic remote trust-anchor replacement or automatic rollback/downgrade. Plan migration/recovery explicitly. Authenticode trust/revocation depends on the Windows trust environment and must be accepted on supported OS versions.

## Verification

Ten update unit cases cover policy validation, real ephemeral Ed25519 signatures/tampering, separation of actions, current-version authentication, downgrade/prerelease/foreign/web rejection, checksum mutation, signature-error rejection, postponement, cancellation/overlap/disposal and safe errors. They use local adapter stubs and generated test keys, not a production certificate/feed. Desktop and final packaged smokes assert unconfigured IPC rejection; the Settings Check control is visibly disabled. Package audit invokes the real Windows verifier and rejects the unsigned private installer. Clean Windows/genuine update acceptance remains blocked on real hosting/signing.

References: [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates), [upstream update guidance](https://www.electron.build/docs/features/auto-update/), [upstream next/v27 signed manifests](https://www.electron.build/docs/features/signed-update-manifests/). NSIS uses electron-updater; Electron's built-in Windows updater targets Squirrel.Windows.
