# P10 design: Calendar, People, memory and preparation

Design recorded before implementation on baseline `153846c`, 2026-10-28. P11 enterprise, P12 mobile and P13 packaging are excluded. Preserve prior incomplete Windows/hardware/DPI/accessibility/endurance/account/P7 acceptance and restricted temporary directories. Final checkpoint results are appended after verification; design alone is not completion evidence.

## Proposed boundaries and checkpoints

1. **Calendar:** independent Google desktop OAuth code/PKCE/state/nonce/system-browser/127.0.0.1 ephemeral loopback; read-only CalendarList/events scopes and minimal OpenID/email identity. Reuse the existing chunked native `KeyringVault` with a Google-only namespace. No hardcoded credentials or embedded authentication. Read-only selected-calendar cache, bounded upcoming-window pagination, cancellation/deletions/recurrences/time-zone-safe rendering, local reminders and explicit link opening. Credentials/setup missing means an honest disconnected/setup state, not invented events.
2. **People:** manual user facts/notes separate from imported Google snapshots. Optional separately consented `contacts.readonly`, explicit search and selected import. Whole-address-book sync only after an additional import-behaviour acknowledgement; support pagination/deltas/deletions/expired token reset. Exact verified email matching, no voice identity/fuzzy aliases. No approved external professional-research provider is configured, so deliver useful local search and explicitly defer external research.
3. **Memory:** independently opt-in encrypted structured records from explicitly selected saved meetings/documents, never temporary text. Prefer deterministic extraction from reviewed P8 decisions/actions/topics/user notes, retaining literal evidence/ref/revision and review state. Reuse P9 ranking for bounded local memory selection with person/topic/meeting/recency/reliability filters. Review/edit/delete/exclude/retention/rebuild controls; source mutation invalidates request guards and removes dependent derivatives. No sensitive-attribute inference or hidden personality profile.
4. **Preparation:** a selected event, selected participant fields, saved-meeting excerpts, reviewed memories and optional active-mode knowledge become bounded untrusted reference entries in the existing P6 context builder/AssistantController. Exact review/removal/new acknowledgement precedes the existing official ChatGPT Responses path. No automatic briefs by default; draft stays ephemeral unless explicitly saved under an acknowledged retention policy. Copy/export/link opening remain deliberate. Detection uses calendar timing only to suggest preparing capture, without process surveillance, capture, joining, saving or Live activation.
5. **Integration:** shared P9 mode/preferences/knowledge, P8 meeting/person/event associations and P7 Live scope. Calendar/contacts/memory are separately selected Live categories with exact source IDs, bound to current account/profile/mode/session and existing cooldown/caps/cancel. No Google connection or memory enablement grants OpenAI permission.

## Storage proposal

Extend the existing PersonalDatabase/worker RPC with versioned, authenticated encrypted record batches. P10 uses the same worker/cipher/OS-key provider in a separate profile database/key namespace, leaving P9's lock/startup semantics intact. Encrypt event details, contact facts/notes, memory/excerpts, settings and chosen saved briefs before SQLite sees them. Only opaque kind/IDs/expiry metadata remains visible. Main-issued scopes and revision/source checks guard every async result and remote send. No renderer paths, tokens, arbitrary SQL, internal reference payloads or network endpoint overrides.

Calendar and Contacts are separate Google grants inside the currently selected local ChatGPT-registration profile; Google subject IDs bind all imported rows. Switching Google identities removes the previous selected connection's cached derivatives while preserving independent P8 meetings/manual local facts. Switching local profiles cancels work, clears snapshots and changes native-vault/key ownership. Restore only explicitly chosen cache/reminder/background-sync policy; never capture or AI grants. Reminders persist dedup receipts before notification delivery, handle changed start/cancellation and only fire from locally cached events. No continuous Google polling: manual refresh by default and optional bounded/backoff periodic read sync.

## Official requirements reviewed

- [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app): public installed clients, external browser, S256 PKCE, random loopback port, state; desktop client secret is optional and never a confidentiality boundary. Google Cloud project/API enablement/Desktop client/consent setup is required. No production verification is claimed. Revocation can invalidate all scopes/clients under the Google project, so Calendar/Contacts are separately consented but cannot promise independent project-wide revocation.
- [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [CalendarList](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list), [events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync): choose `calendar.calendarlist.readonly` and `calendar.events.readonly`, never writes. A bounded past/future window with `singleEvents=true` provides finite recurrence instances and cache sizes. `syncToken` disallows timeMin/timeMax/orderBy and can expire with 410; do not combine it with the window or falsely advertise incremental Calendar sync. Complete paginated window replacements are atomic; bounded 410 recovery restarts the window once, while failed/incomplete refreshes retain a visibly stale prior cache.
- [People contacts](https://developers.google.com/people/v1/contacts), [connections.list](https://developers.google.com/people/api/rest/v1/people.connections/list), [searchContacts](https://developers.google.com/people/api/rest/v1/people/searchContacts): search needs an empty warmup request; use only names/email/organisation metadata needed for user-selected records. Full opt-in connection sync uses stable parameters and `requestSyncToken`; token expiry after seven days/EXPIRED_SYNC_TOKEN requires a full resync. Selected import does not silently become whole-book sync.
- [OpenID validation](https://developers.google.com/identity/openid-connect/openid-connect), [production policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance): verify Google signing keys/issuer/audience/nonce/subject/time claims; protect refresh tokens; request minimum scopes, separate development/production projects and complete applicable consent/brand/sensitive-scope/domain/privacy verification before public distribution. Client ID/configuration and genuine test-account permissions must be supplied; no credentials are fabricated.
